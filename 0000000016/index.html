一、基础概念

  • 密钥对：一个公钥 + 一个私钥。公钥公开，私钥保密。
  • 公钥：用于加密和验证签名。
  • 私钥：用于解密和签署文件/提交。
  • Key ID：密钥的唯一标识符（通常是最后8位或16位十六进制）。
  • 密钥环：存放密钥的数据库（pubring.kbx / secring.gpg）。
  • 信任网络：通过互相签名建立的信任体系（Web of Trust）。

九、安全最佳实践

  1. 私钥绝不上传网络，备份到加密 U 盘或硬件安全密钥（如 YubiKey）。
  2. 定期延长有效期（例如每年一次）。
  3. 使用强密码保护私钥（至少 12 位，含大小写+数字+符号）。
  4. 撤销证书：生成密钥时同时生成撤销证书 gpg --gen-revoke <Key ID>，并存放在安全地方（万一私钥泄露可用它宣告该密钥作废）。
  5. 在公共电脑上避免使用 --import 私钥，改用 --encrypt 和 --decrypt 时要确保环境可信。

十、常见错误信息及解决

错误信息 含义 解决方法
No secret key 找不到私钥 检查user.signingkey 或 --recipient 是否正确，确认密钥已导入且未被删除。
gpg: signing failed: Inappropriate ioctl for device 无法弹出密码输入窗口 设置环境变量export GPG_TTY=$(tty)（Linux/macOS）或安装 pinentry。
gpg: keyblock resource ...: No such file or directory 路径转换错误（Windows 常见） 设置set MSYS_NO_PATHCONV=1 或清除 GNUPGHOME 环境变量。
gpg: Can't check signature: No public key 缺少对方的公钥 用gpg --recv-keys 下载对方公钥。
gpg: Invalid passphrase 密码错误 确认密码大小写，或重新设置私钥密码（gpg --edit-key <Key ID> → passwd）。

十一 密钥撤销证书

撤销证书是你在私钥丢失、泄露或更换邮箱时，用来通知外界你的公钥作废的“紧急销毁开关”。 必须提前生成并妥善保管。

整个流程分为生成、保存和发布三步：

1. 提前生成撤销证书（✅ 推荐）

生成密钥对后，应立即生成撤销证书。这让你在忘记密码或私钥泄露时，仍有办法控制公钥的“生死”。

2. 严格保存

把生成的 mykey_revoke.asc 文件离线存放在安全的地方，例如加密U盘。绝对不要放在日常使用的 .gnupg 目录下，以免被误用或连同私钥一起丢失。

例如，使用 keys.openpgp.org 服务器。

⚠️ 重要警告

如果私钥丢失且没有提前生成撤销证书，则无法撤销该公钥。因此，这是密钥管理中不可跳过的安全步骤。
撤销证书的使用分为两步：先在本地导入使密钥失效，再同步到公钥服务器通知他人。

一、何时需要使用撤销证书？

  • 私钥丢失或忘记密码
  • 私钥被泄露（被盗、病毒等）
  • 更换新密钥（旧密钥不再使用）
  • 邮箱地址变更，不再使用旧密钥

一旦导入撤销证书，该密钥在你本地就会标记为“已撤销”，之后不能再用于签名或解密（但之前已签名的数据仍可验证）。

四、重要安全提示

  1. 撤销证书不要随意导入，一旦导入就不可逆。仅在你确实要废弃该密钥时使用。
  2. 导入撤销证书不需要私钥（即使私钥已丢失也可操作）。所以保管好撤销证书本身很重要，防止他人恶意撤销你的密钥。
  3. 撤销后的密钥无法恢复。如果只是暂时不用，可以延长有效期或降低信任，而不是直接撤销。

四、常见问题

Q：我指定了 Key ID，但报错 No secret key？
A：检查 Key ID 是否正确（gpg --list-secret-keys 查看），注意大小写，通常用完整长 ID（如 3DA13E2330595E7C）更准确。

Q：能不能用邮箱代替 Key ID？
A：可以，但前提是邮箱只有一个对应的私钥。若多个私钥绑定了同一邮箱，需要用 Key ID 区分。

Q：如何临时忽略默认配置，强制使用另一个密钥？
A：在 git commit 时加上 --gpg-sign=<其他Key ID> 即可覆盖 user.signingkey。

五、一句话总结

  • GPG 命令：用 -u <Key ID> 或 --local-user
  • Git 提交：用 git commit -S<Key ID> 或设置 user.signingkey

十四 最大化隐私（隐藏私钥信息）

--throw-keyids 是 GPG 加密时的一个隐私增强选项。它的作用是：在加密数据的元数据中，不显式记录接收者的密钥 ID。

一、默认行为 vs --throw-keyids

默认加密（不加此选项）

加密后的数据包中会包含一个“密钥 ID 列表”，明确写着“这个加密包是发给 alice@example.com 的公钥（Key ID xxxx）的”。任何拥有该公钥的人都能从密文元数据中直接看到接收者是谁（虽然无法解密）。

使用 --throw-keyids

加密后的数据包中，接收者密钥 ID 字段被填充为全零（或随机垃圾值），不泄露任何关于接收者身份的信息。攻击者拿到密文后，无法判断这是发给 Alice、Bob 还是 Charlie 的。

二、工作原理

  1. 正常情况下，GPG 将接收者的 Key ID 明文明文写在加密包的 Pubkey-Encrypted Session Key 包中。
  2. 使用 --throw-keyids 后，GPG 将这个 Key ID 字段设为 0x0000000000000000（8 字节零）。
  3. 解密时，接收方必须用自己所有的私钥依次尝试解密会话密钥，直到某个私钥成功解开。
    • 如果你只有 1~2 个私钥，这个尝试过程很快（微秒级）。
    • 如果你有几十个私钥，也基本无感知。

三、适用场景

场景 是否推荐 --throw-keyids
匿名举报、泄露敏感信息（不希望暴露接收者身份） ✅ 强烈推荐
发送加密文件给特定同事（对方是你唯一接收人） ⚠️ 可选，但通常没必要
多人加密（--recipient 列出多个接收者） ⚠️ 需注意：所有接收者都会尝试各自的私钥，但密文体积会增大
自动化脚本、批量处理 ❌ 不推荐（增加解密端处理时间）
接收方使用硬件密钥（如 YubiKey）且私钥较多 ⚠️ 可能触发多次 PIN 输入，体验差

六、注意事项

  1. 兼容性：所有现代 GPG 版本都支持 --throw-keyids，解密时会自动尝试所有私钥。
  2. 性能影响：解密端需要遍历所有私钥，通常可以忽略（现代 CPU 毫秒级）。如果私钥数量 > 100 或使用智能卡（每次尝试需按确认），会明显变慢。
  3. 匿名性增强：即使加密数据被截获，攻击者不知道你发给谁。但仍需注意其他元数据（如文件名、时间戳、通信模式分析等）。
  4. 与密钥服务器的矛盾：如果使用 --throw-keyids 加密，但接收者的公钥仍公开在密钥服务器上，攻击者仍可推测可能发给该用户。真正的强匿名需要配合 Tor 等使用。

七、总结

--throw-keyids 让你的加密输出“对暗号”：只给出一串密文，不告诉这是给谁的。只有拿着正确私钥的人才能试出来。

适用：匿名通信、高度敏感的隐私保护场景。
不适用：日常办公、团队协作（增加复杂度，收益极低）。

十五 配置硬件密钥

是的，这正是现代加密实践中，用来保护私钥的最高安全方案。它的核心思想是把你的私钥，从随时可能被黑的电脑里，移到一个独立的、专为安全设计的硬件设备中。

下面从原理、优势到实战操作，一步步为你讲解。

什么是硬件密钥？

硬件密钥（如 YubiKey、Nitrokey 或智能卡），本质上是一个专门设计的、能独立执行密码运算的微型计算机。

  • 不可提取性：私钥一旦写入设备，就会立刻锁定，永远无法以任何形式被读取或导出。攻击者即使完全控制了你的电脑，也无法通过网络偷走你的私钥。
  • 运算隔离：加密/解密、签名/验证等密码操作，都在硬件内部完成。系统只将待处理数据和指令发送给设备，设备处理后再将结果返回，私钥全程不进入计算机内存。
  • 防篡改设计：设备芯片本身设计为防篡改的，任何物理拆解都会导致内部电路自毁，保护数据安全。

为什么需要硬件密钥？核心优势

使用硬件密钥，相当于把你的身份凭证（私钥）从“软件”升级到了“硬件”级别，提供了多重保障。

  • 🔒 防软件层面的黑客攻击：恶意软件无法扫描磁盘找到私钥文件，也不能从内存中提取私钥，因为它根本就不在电脑里。
  • 🙌 物理接触授权：为所有敏感操作增加一个物理确认的动作，必须在设备上按下按钮才能完成，防止远程操控。
  • 🤸 便携与跨平台：把密钥插在任何一台电脑上就能工作，无需手动分发和配置私钥文件，而且PIN码可以独立于电脑设置。
  • 🛡️ 防止“加密勒索”：即使忘记拔下YubiKey，攻击者也只能在你连接时临时借用，而无法将你的私钥从设备中复制走。

哪些硬件密钥可以选？

只要支持 OpenPGP 智能卡规范的设备都可以使用。

  • YubiKey 5 系列：是市面上最流行、兼容性最好的选择之一。选购时请务必选择 YubiKey 5 系列，并确认其支持 OpenPGP 功能，以确保可以进行签名和认证。
  • Nitrokey / GNUK：完全开源的硬件方案，适合追求极致透明度的用户。
  • TKey / LibreKey：其他兼容 OpenPGP 规范的 USB 设备，同样可以作为备选。
  • PC/SC 智能卡：需要单独的读卡器，在企业环境中也有应用。

十六 大型文件加密与签名

对于极大型文件（例如几十GB的数据库备份或虚拟机镜像），直接使用 GPG 加密可能遇到内存压力、压缩效率低下或单文件操作不便等问题。你提到的几种方式正是解决这些问题的常用技巧。

下面依次解释 GPG 压缩行为、--compress-algo 与 split 的配合，以及 gpg --symmetric + tar 的专业做法。

一、GPG 默认压缩行为

GPG 在加密前会先对数据进行压缩（除非你使用 --compress-algo none）。默认压缩算法通常是 ZIP（或 ZLIB）。这对普通文件很有好处：

  • 减少密文体积
  • 增加破解难度（压缩破坏了已知明文模式）

但对极大型文件（尤其是已被压缩的视频、数据库备份），压缩可能：

  • 浪费大量 CPU 时间
  • 需要大量临时内存
  • 几乎不减小体积

场景 推荐命令 理由
单个已压缩的大文件（如 .zip, .mp4, .iso） gpg --compress-algo none --symmetric 避免浪费 CPU 重新压缩

“更专业的做法” 之所以专业，是因为它结合了 Unix 管道哲学：tar 负责归档（和可选压缩），gpg 负责加密，两者解耦，可灵活替换压缩算法或加密方式，且完全避免落盘，适合自动化脚本和大型备份任务。

十七 更多加密算法

现代 GPG 推荐：Ed25519 / Curve 25519 椭圆曲线密钥

传统的 RSA 密钥（2048/4096 位）虽然广泛使用，但存在密钥较长、生成慢、签名/解密性能较低的缺点。现代 GPG (>=2.1) 全面支持基于椭圆曲线的 Ed25519 签名算法和 Curve 25519 加密算法，它们具有：

  • 更短的密钥：公钥仅 32 字节（RSA 4096 位为 512 字节）
  • 更强的安全性：~128 比特安全强度（相当于 RSA 3072）
  • 更快的速度：生成、签名、验证均比 RSA 快数倍
  • 更小的签名：签名长度固定 64 字节
  • 现代标准：被 OpenSSH、TLS 1.3、Signal 等广泛采用

  • 符合最佳实践：GPG 默认架构就是主密钥 + 子密钥。

三、Ed25519 密钥的日常使用注意事项

✅ 优点体验

  • 生成几乎瞬间完成（比 RSA 4096 快一个数量级）。
  • 签名提交（git commit -S）和验证非常快。
  • 导出公钥（gpg --export --armor）只有几行，便于分享。

⚠️ 兼容性问题

  • 旧版 GPG (<2.1) 不支持 Ed25519。如果你的同事使用 CentOS 7 等旧系统，可能无法验证你的签名。
  • 某些平台（如 GitLab 旧版本）虽支持 GPG，但可能未更新 Ed25519 解析库。现代主流平台（GitHub、GitLab 最新版）均已支持。
  • 解决方法：如果必须兼容旧系统，可以同时生成一个 RSA 子密钥用于加密，或保留一个 RSA 备用密钥。

🔐 安全性说明

  • Ed25519 签名是确定性的（无随机数依赖），避免了因随机数生成器缺陷导致私钥泄露的风险。
  • Curve 25519 在设计上侧信道攻击抵抗力更强。
